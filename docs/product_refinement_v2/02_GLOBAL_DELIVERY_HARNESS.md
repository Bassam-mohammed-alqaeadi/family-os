# Global Delivery Harness — Product Refinement V2

> **Status:** Running
> **Mode:** One connected platform; one pillar at a time; shared foundation always visible.
> **First pillar:** Security & Digital Safety.

## 1. What this harness prevents

The harness prevents attractive but disconnected screens, imaginary technical promises, undocumented scope drift, and late discovery of failure states. It gives every pillar the same professional path from evidence to build readiness.

## 2. Working lanes

Each active pillar moves through five lanes in parallel. A finding in one lane can send work back to another; no document advances merely because it was written.

| Lane | Core question | Outputs |
|---|---|---|
| Evidence & market | What exists today, what do families need, and where are global alternatives strong or weak? | Evidence map, competitor/parity map, assumptions register. |
| Product & strategy | What job is the system hired to do, for whom, and what belongs in which release? | Product narrative, system classification, value and success measures. |
| UX & visual design | What does every person see, do, understand, and recover from? | IA, journeys, screen/state map, visual direction, settings desk. |
| Capability & architecture | What can the platform truthfully do and what is required to deliver it? | Device/capability matrix, data/events, service contracts, dependencies. |
| Quality & operations | How does this remain reliable, safe, supportable, and measurable? | Edge-case model, acceptance criteria, test strategy, operational plan. |

## 3. The loop

```text
FRAME → DISCOVER → DESIGN → CHALLENGE → RECONCILE → VERIFY → GATE → RECORD
  ↑                                                               │
  └────────────── repair or deepen when evidence is insufficient ┘
```

### FRAME
State the user outcome, in-scope systems, dependencies, exclusions, and completion test.

### DISCOVER
Inspect code, registries, current UX, platform capabilities, global alternatives, and unanswered questions. Facts are separated from assumptions.

### DESIGN
Create the product model, journeys, screen/state map, visual hierarchy, settings model, and cross-platform interactions.

### CHALLENGE
Run the work through product, UX, visual, engineering, reliability, trust, accessibility/localization, and operational lenses. Deliberately test failure, conflict, timing, misuse, and unsupported-device cases.

### RECONCILE
Resolve contradictions, remove duplication, close loops, record the decision, and preserve only one current version of each artifact.

### VERIFY
Check traceability from system → service → journey → screen/state → settings → capability → acceptance criterion. Verify that platform-spine connections are explicit.

### GATE
Bring only the necessary decision package to the Owner: clear recommendation, alternatives, consequences, and requested approval.

### RECORD
Update the decision register and loop pointer. The next task begins only when the prior one has a clear outcome.

## 4. Autonomy model

### Green — autonomous work

The delivery partner proceeds without interrupting the Owner for code/registry inspection, discovery, competitor research, system mapping, UX analysis, visual proposals, technical feasibility mapping, self-review, documentation, and internal quality checks.

### Amber — concise Owner decision

The delivery partner presents a recommendation when a choice materially affects product positioning, inclusion sequence, interaction intensity, or visual direction. The decision package contains the question, options, recommendation, impact, and a reversible default where possible.

### Red — approval required before proceeding

Stop for approval before an irreversible product promise, a newly invasive capability, a release commitment, a move of a Future Development into active scope, or any Backend/Native start.

## 5. Gates for the Security pillar

| Gate | Name | Required evidence | Owner decision needed? |
|---|---|---|---|
| G0 | Program bootstrap | Charter, system universe, decisions, loop running. | Recorded by activation. |
| G1 | Security direction | Product promise, role model, 12-system map, inclusion hypotheses, market/evidence findings. | Yes — scope/direction approval. |
| G2 | Security UX lock | IA, journeys, all key screens/states, parent settings desk, child clarity model, visual direction. | Yes — experience approval. |
| G3 | Security build readiness | Capability truth, data/event contracts, dependencies, edge cases, acceptance tests, implementation sequence. | Yes — authorize later engineering work. |
| G4 | Security feature complete | Implemented, tested, truthful feature behaviour. | Later; not part of current refinement. |
| G5 | Security release ready | Operational readiness, support, analytics, release checks, pilot feedback. | Later; not part of current refinement. |

## 6. Artifact standard

Every artifact must state:

- Its purpose and decision it supports.
- Evidence used and assumptions still open.
- Scope and explicit non-scope.
- A named owner/role for each action.
- Links to the shared platform spine.
- Acceptance criteria or a clear next decision.
- Last update and current status.

## 7. Definition of a completed refinement loop

A loop is complete only when the user value, journeys, visual and interaction states, settings, capability truth, reliability cases, cross-platform dependencies, success measures, and implementation handoff are mutually consistent. A beautiful happy path alone fails this definition.
