# منهجية العمل على GitHub — Family OS

> **القاعدة الواحدة التي تختصر كل شيء:**
> **مساحة العمل مؤقتة، والمستودع على GitHub هو المصدر الوحيد للحقيقة.**
>
> كل ما لا يوجد على GitHub، اعتبره غير موجود. وكل ما يوجد على GitHub، يمكن استعادته
> في أي لحظة بأمرين: `clone` ثم `install`.

هذه الوثيقة ليست نظرية — كل قاعدة فيها وُلدت من خطأ حقيقي حدث وتمّ تجاوزه. القسم ٧ يسرد
الحوادث الحقيقية التي أنتجت هذه القواعد.

---

## ٠) المبدأ الحاكم وما يتبعه

| المبدأ | ما يعنيه عملياً |
|---|---|
| مساحة العمل مؤقتة | لا تبنِ عادة الاعتماد على وجود ملف لم يُودَع. الجهاز قد يُعاد بناؤه في أي لحظة. |
| GitHub هو الحقيقة | الحكم النهائي على «هل أنجزنا؟» هو ما في الفرع المدفوع، لا ما في ذاكرتك. |
| المستودع للمصدر فقط | لا مُشتقّات، لا مكتبات منزَّلة، لا أرشيفات. المستودع يبقى خفيفاً إلى الأبد. |
| الاستعادة = clone + install | أي شخص يستطيع البدء من الصفر بأمرين. هذا هو الاختبار الحقيقي للنظافة. |

**معيار القبول:** لو مُسحت مساحة العمل الآن، يجب ألّا يضيع أي شيء. أداة
`tools/git/repo-health.sh` تجيب على هذا السؤال في ثوانٍ.

## ١) القواعد السبع

### القاعدة ١ — لا عمل ذو قيمة خارج Git
أي تعديل يزيد عن «سطرين للتجربة» يجب أن ينتهي بإيداع ودفع في نفس الجلسة.

> **لماذا:** في هذه الجلسة أُعيد بناء مساحة العمل مرتين، وضاعت الإيداعات المحلية في
> إحداهما. العمل كان محفوظاً **فقط** لأنه كان قد دُفع.

### القاعدة ٢ — الإيداع وحدة صغيرة مكتملة
إيداع واحد = تغيير منطقي واحد قابل للفهم والمراجعة.

- ✅ «أضف اختبار واجهة عربي RTL للنموذج» — تغيير واحد
- ❌ «إصلاحات متنوعة» — لا يمكن مراجعته ولا الرجوع عنه

**التزامن لا التكديس:** كل إيداع يجب أن يترك المستودع في حالة صالحة. لا تُودِع نصف ميزة
معطّلة ثم تُكمل لاحقاً.

### القاعدة ٣ — رسالة الإيداع تحمل الدليل، لا النية
الرسالة تجيب على ثلاثة أسئلة: **ماذا تغيّر؟ لماذا؟ وكيف تحقّقت؟**

```
نوع(نطاق): صف الفعل في صيغة الأمر

لماذا كان هذا مطلوباً — السبب الحقيقي، لا الوصف.

ما الذي تغيّر فعلاً، ومن أي حالة إلى أي حالة.

كيف تحققت: الأمر الذي شغّلته ونتيجته الحقيقية بالأرقام.
رقم التشغيل على CI إن وُجد.
```

**ممنوع منعاً تاماً:** أن تكتب «الاختبارات ناجحة» قبل تشغيلها. النية ليست دليلاً.

### القاعدة ٤ — كل مُشتقّ ممنوع من التاريخ
لا `node_modules`، لا `build/`، لا `.dart_tool`، لا `.zip`، لا مفاتيح.

> **لماذا:** تاريخ Git لا يُمحى. ملف كبير دخل مرة يبقى في كل استنساخ إلى الأبد. المستودع
> يصبح بطيئاً ثم ثقيلاً ثم غير قابل للعمل.

**الأصول الكبيرة** (فيديو، تصميمات، نماذج): تُرفع كـ **Release asset** أو تخزين خارجي
ويوضع لها رابط في المستودع. لا تدخل التاريخ أبداً.

### القاعدة ٥ — لا force-push على main أبداً، ولا حذف فرع غير مدموج قبل أرشفته
`git push --force` يمحو تاريخاً ربما يعتمد عليه عمل آخر. عند أي تعارض أو فوضى، الحل دائماً
إلى الأمام: تفقّد، تحقّق، أعد الإيداع.

**سياسة الفروع (قرار المالك، أكتوبر ٢٠٢٦ — توحيد التطوير على `main`):**
- `main` **هو الفرع الوحيد طويل العمر**، وهو مصدر الحقيقة الوحيد.
- كل تغيير يمر بفرع قصير العمر يتفرّع من `main` ← طلب دمج ← CI أخضر ← دمج بـ**merge commit**
  (لا squash ولا rebase، حفاظاً على بصمات الإيداعات التي تستشهد بها وثائق الحلقة).
- الفرع المدموج يُحذف عند الدمج، ولا يعيش أكثر من طلب دمج واحد.
- **لا يُحذف فرع غير مدموج إلا بعد وضع وسم أرشيفي مشروح `archive/*` على رأسه** والتحقق منه
  على GitHub (`git ls-remote --tags origin`). الوسوم الأرشيفية لا تُحذف أبداً.
- كل الفروع القديمة (`arena/*` وغيرها) أُرشفت بوسوم `archive/*` ثم حُذفت يوم التوحيد؛
  لاستعادة أي منها: `git fetch origin tag archive/<الاسم>` ثم `git switch -c <فرع> archive/<الاسم>`.

### القاعدة ٦ — الفحص قبل الدفع، والحكم النهائي من CI
قبل كل دفعة شغّل ما تستطيع تشغيله محلياً. وما لا تستطيع تشغيله محلياً، لا تدّعِ نجاحه —
انقله إلى CI وانتظر حكمه.

### القاعدة ٧ — الاختلاف يُسجَّل ولا يُخفى
إذا فشل اختبار، أو رُفض طلب، أو تعذّر شيء — يُكتب في السجل كما هو. السجل الصادق يُبنى عليه،
والسجل المُجمَّل ينهار عند أول ضغط.

## ٢) الدورة اليومية — الخطوات والأوامر

### ٢.١ بداية الجلسة: مزامنة وتحقّق
```bash
cd <repo>
git fetch origin
git status -sb                 # هل أنا على الفرع الصحيح؟ هل معي إيداعات محلية؟
git log --oneline -5           # أين وصل العمل؟
tools/git/repo-health.sh       # هل مساحة العمل آمنة؟
```
**إن كان هناك إيداعات محلية غير مدفوعة، ادفعها أولاً قبل أي عمل جديد.**

### ٢.٢ أثناء العمل: إيداع كل وحدة مكتملة
```bash
git add -A
git commit -m "<رسالة تحمل الدليل — القاعدة ٣>"
```

**نصيحة عملية:** ادفع قبل تشغيل أي اختبار طويل. إن فشل الاختبار فأنت تعرف أي تغيير سبّبه،
والعمل محفوظ في كل الأحوال.

### ٢.٣ نهاية الجلسة: ثلاثة أوامر لا تُنسى
```bash
git add -A && git commit -m "..."     # ١) كل تغيير محفوظ
git push origin <branch>              # ٢) كل شيء على GitHub
tools/git/repo-health.sh              # ٣) دليل أن مساحة العمل آمنة للتخلّي عنها
```

## ٣) الاستعادة الكاملة — إن ضاعت مساحة العمل

```bash
git clone https://github.com/<owner>/<repo>.git
cd <repo>
git switch <branch>

# ثم أعد فقط ما هو مُشتق (لا يأتي من Git أبداً):
npm ci  --prefix backend        # مكتبات Node
flutter pub get                 # مكتبات Dart
```

هذا كل شيء. إن احتجت خطوة إضافية فالمستودع ليس نظيفاً — أضف ما نقص إلى التوثيق أو إلى
`.gitignore`.

### ٣.١ استعادة إيداعات محلية ضاعت بسبب إعادة بناء مساحة العمل
```bash
git fetch origin
git reset --soft origin/<branch>       # انقل HEAD إلى رأس الريموت مع إبقاء الملفات
git diff --cached --stat               # تحقّق: هل هذه فعلاً تعديلاتي؟
git checkout -- .                      # نظّف الشجرة إن كانت الملفات مطابقة أصلاً
```
**قبل الحذف:** تحقّق أن محتوى كل ملف غير مُودَع موجود في تاريخ المستودع (الأداة تفعل ذلك
تلقائياً في الخطوة ٢). **لا force-push في أي حال.**

## ٤) قراءة CI بصدق

هذه أهم مهارة عملية، وفيها مكامن خداع حقيقية.

### ٤.١ فخ `continue-on-error`
خطوة تحمل `continue-on-error: true` تُسجَّل **`success` وهي فاشلة**. الحكم الحقيقي في خطوة
«الإنفاذ» (Enforce) التي تلخّص البوابات.

**القاعدة:** لا تقرأ نتيجة CI من ملخّص التشغيل. اقرأ من مصدر الحقيقة:
```bash
gh api repos/<owner>/<repo>/actions/runs/<run_id>/jobs \
  --jq '.jobs[].steps[] | "\(.conclusion)\t\(.name)"'
```
علامة النجاح الحقيقية: **خطوة الإنفاذ = `skipped`**. (تُشغَّل فقط عند وجود فشل.)

### 4.2 نص الفشل الحقيقي — من الـannotations
سجلات المهام قد تكون غير قابلة للقراءة (تخزين خارجي محجوب). الـannotations تعمل دائماً
وتحمل نص الفشل الكامل وقائمة الاختبارات الناجحة:
```bash
gh api repos/<owner>/<repo>/check-runs/<job_id>/annotations \
  --jq '.[] | select(.annotation_level=="failure") | .message'
```

### ٤.٣ مشكلة «لم يُحجز رُندر»
قد تبقى مهمة في الطابور ثم تُلغى مع `runner_name: ""` ورسالة
*"The job was not acquired by Runner of type hosted"*. **هذا ليس فشل كود** — هذه بنية
تحتية. سجّلها كما هي، وأعد المحاولة بدفعة جديدة، ولا تخلطها بفشل حقيقي في السجل.

### ٤.٤ التفريق بين «فشل موروث» و«فشل أدخلته أنت»
قبل أن تبدأ، شغّل CI على **الالتزام الأساسي** وسجّل الأرقام (عدد الناجح/الفاشل). بعد عملك
شغّله مجدداً. **إن بقي عدد الفاشل كما هو وزاد الناجح، فأنت لم تُدخل فشلاً.** هذا هو
«الكناري» (canary):

| الالتزام | ناجح | فاشل | الاستنتاج |
|---|---|---|---|
| الأساس | 1781 | 2 | — |
| بعد عملي | 1784 | 2 | أضفت ٣ ناجحة، ولم أُدخل أي فشل |

## ٥) الأداة

```bash
tools/git/repo-health.sh
```

تجيب على سؤال واحد: **«لو انتهت مساحة العمل الآن، هل سأفقد شيئاً؟»**

| القسم | ما يفحصه |
|---|---|
| ١ | الفرع، الإيداعات غير المدفوعة، التخلّف عن الريموت، `detached HEAD` |
| ٢ | الملفات غير المُودَعة — وهل محتواها موجود في تاريخ المستودع أم أنه عمل وحيد |
| ٣ | مجلدات مُشتقّة متتبَّعة، ملفات أكبر من 2 MiB، أرشيفات وتنفيذيات، حجم `.git` |
| ٤ | المفاتيح والأسرار — **بفحص المحتوى لا الاسم** — ومطابقة الحارس الرسمي للمستودع |
| ٥ | تغطية `.gitignore` لكل نمط مُشتقّ شائع |

`exit 0` = آمن. `exit 1` = هناك ما يستحق التوقف عنده.

## ٦) القوالب الجاهزة

### قالب رسالة الإيداع
```
نوع(نطاق): الفعل وما تغيّر

لماذا: السبب الحقيقي للمشكلة.

التحقّق: الأمر → النتيجة بالأرقام (مثال: 93/93 ناجح، 0 فاشل).
CI: <run_id> → النتيجة.
```

### قالب سجل تشغيل في CI
| الالتزام | التشغيل | الحالة | ملاحظة |
|---|---|---|---|
| `3d7ff18` | Flutter CI `37372946441` | ✅ | كل الخطوات خضراء، خطوة الإنفاذ `skipped` |
| `3d7ff18` | Foundation Gate CI `37372946356` | ⛔ | لم يُحجز رُندر (بنية تحتية) — لا علاقة بالكود |

### قالب تسجيل فشل
```
العَرَض:  الرسالة الحرفية من CI.
السبب الجذري:  ماذا كان الكود يفعل فعلاً.
الإصلاح:  ما تغيّر، وإلى أي حالة.
التحقّق:  كيف أُثبت أن الإصلاح صحيح — بالأرقام.
```

## ٧) حوادث حقيقية وُلِدت منها هذه القواعد

| الحادثة | ما حدث | القاعدة التي وُلدت |
|---|---|---|
| ضياع إيداعات محلية | أُعيد بناء مساحة العمل، فعاد الكلون إلى التزام قديم والريموت أمامه | القاعدة ١ + §٣.١ |
| «الاختبارات ناجحة» كذبة | خطوات `continue-on-error` تُسجَّل `success` وهي فاشلة | §٤.١ |
| فشل موروث نُسب للعمل الجديد | كان في الأساس فشلان قديمان (١٧٨١/٢) — كاد يُظن أنهما من العمل الجديد | §٤.٤ |
| رُندر لم يُحجز | مهمة بقيت في الطابور ثم أُلغيت برسالة «not acquired» | §٤.٣ |
| التوكن للقراءة فقط | محاولة استدعاء Workflow عبر REST API رُفضت `403` بينما القراءة `200` | §٤ — الصلاحية ليست عطلاً |
| ملف CRLF | تعديل ملف بنهايات أسطر Windows عبر أدوات نصية يفسد الملف | §٨ |
| إنذار كاذب في الفحص | فحص أسماء الملفات اتهم حارس الأسرار نفسه | §٥ — الفحص على المحتوى |

## ٨) تفاصيل تقنية تحمي من أخطاء صامتة

- **نهايات الأسطر:** بعض ملفات Dart تستخدم `CRLF`. عدّلها بأدوات تحفظ البايتات، وتحقّق
  بعدّاد قبل وبعد. الخطأ هنا لا يظهر في المراجعة العادية.
- **أذونات الملفات التنفيذية:** سكربت جديد يحتاج `chmod +x`، وإلا فشل صامتاً عند التشغيل.
- **ملفات القفل:** استخدم `--enforce-lockfile` (Flutter) و`npm ci` (Node) لضمان بناء
  مطابق تماماً لما اختُبر.
- **التوليد المُلتزم:** إن كان الملف المولَّد مُتتبَّعاً في Git، فشغّل خطوة التوليد في CI
  وتحقّق أن لا فرق — وإلا انحرف المولَّد عن المصدر بصمت.

## ٩) الملخّص في تسعة أسطر

1. ادفع قبل أن تنام، وقبل أن تجرّب، وقبل أن تفكّر.
2. إيداع واحد لتغيير واحد.
3. رسالة الإيداع تحمل رقماً حقيقياً، لا رأياً.
4. لا شيء مُشتقّ يدخل التاريخ.
5. لا force-push، و`main` هو الفرع الوحيد طويل العمر؛ لا حذف لفرع غير مدموج قبل وسم `archive/*`.
6. لا تدفع شيئاً لم تتحقّق منه، ولا تدّعِ ما لم تشغّله.
7. اقرأ CI من الـjobs والـannotations، لا من الملخّص.
8. سجّل الفشل كما هو.
9. شغّل `tools/git/repo-health.sh` في نهاية كل جلسة، واقرأ `exit 0`.
